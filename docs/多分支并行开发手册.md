# 多分支并行开发手册 · 事务伴侣

> 定位：本手册是 `开发驱动文档/00-驱动开发规则.md` **11.7-C（git worktree 并行开发）的操作细则**，
> 不改动 11.7 的任何权责边界（main=事实线、分支只改代码、编号权在 main 等条款一律不变）。
> 版本：v1.0（2026-09-06，AI 受托编制）

---

## 0. 一句话原理（先讲人话）

以前是**一支装修队在一套房子里干活**：改完厨房才能改卧室，改卧室时厨房的活全得停着，你在旁边干等。

现在改成：**把这套房子复制成几套一模一样的样板间**（这就是 git worktree——同一个仓库，多个目录同时检出不同分支），
每个工人进自己那套样板间改自己负责的房间，互不干扰；全改完了，工头再把各套的改动**统一贴回主屋**（合并回 main）。

- **房子 = 代码仓库**（只有一份，在 `.git` 里）
- **样板间 = worktree 工作目录**（每个分支一个目录）
- **工人 = 一个 WorkBuddy 对话窗口**（一个窗口只能认一个工作目录，所以"多窗口 = 多分支"）
- **工头 = 你开的主对话窗口**（在主目录 main 上，只派单和收口，不写功能代码）

---

## 1. 角色分工（谁干什么，一表看清）

| 角色 | 工作目录 | 分支 | 干什么 | **不干什么** |
|---|---|---|---|---|
| **工头**（1 个主对话） | `D:\000-me-work\事务伴侣` | main | 派单、盯进度、合并收口、跑 verify、出交付物 | 不写功能代码（避免和工人抢文件） |
| **工人**（N 个对话） | `D:\000-me-work\wt-<任务名>` | feat/xxx | 只写自己那块代码 + 自测 + 提交 | 不碰五文档、不切分支、不改别人的文件 |

> **关键认知**：WorkBuddy 的对话窗口是**绑定工作目录**的。所以"开一个新对话 = 开一个新工人"，
> 前提是它得有一个自己的目录。这就是 worktree 的意义——没有它，两个窗口改的是同一批文件，会互相踩踏。

---

## 2. 目录与命名规矩

| 东西 | 命名 | 例子 |
|---|---|---|
| 分支 | `feat/<功能>` 或 `exp/<试验>` | `feat/voice-ui` |
| worktree 目录 | `D:\000-me-work\wt-<任务短名>` | `D:\000-me-work\wt-voice-ui` |
| 编译车间 | `D:\sw_build-<任务短名>` | `D:\sw_build-voice-ui` |
| 任务单 | worktree 目录里的 `_任务单.md` | 自动生成的干活说明书 |
| 主仓车间（工头专用） | `D:\sw_build` | 只有工头能用 |

命名转换规则：分支名去掉前缀、斜杠转连字符（`feat/voice-ui` → `voice-ui`）。脚本自动处理，你只管给分支名。

---

## 3. 三步走：派单 → 干活 → 收口

### 步骤 1 · 派单（工头会话执行一条命令）

```powershell
powershell -File tools\parallel_dev.ps1 new -Task "feat/voice-ui" -Goal "语音按钮改成长按说话" -Files "app/lib/pages/chat_page.dart" -Standard "flutter test 全绿，长按录音松手发送"
```

这条命令会自动做完四件事：

1. 建分支 `feat/voice-ui`（从 main 最新提交切出）
2. 建独立目录 `D:\000-me-work\wt-voice-ui`
3. 建独立编译车间 `D:\sw_build-voice-ui`，并把源码同步过去预热（含依赖拉取，耗时 1-3 分钟）
4. 生成 `_任务单.md`（写清目录、分支、任务、可改文件、完成标准、禁止事项）

然后你**开一个新的 WorkBuddy 对话 → 把工作区切到 `D:\000-me-work\wt-voice-ui` → 把任务单内容粘进去**，工人就开工了。
你想同时推三个任务，就重复三次、开三个窗口，它们各干各的，你不用来回等。

### 步骤 2 · 工人干活（每个窗口里的 AI 自觉遵守）

- **只改任务单里圈定的文件**（越界就是给收口埋雷）
- **不碰五文档、不碰 START_HERE、不碰 verify.py**（编号权和事实线只在 main）
- **自测**：`flutter test`（在自己车间里跑：`cd D:\sw_build-voice-ui`）
- **编译验证**：`powershell -File tools\build_all.ps1 -Project D:\000-me-work\wt-voice-ui -Workshop D:\sw_build-voice-ui`
- **干完提交**，并在对话最后输出一行固定格式的完工报告（工头照这个批量收）：

```
BRANCH_DONE | feat/voice-ui | 改动文件: app/lib/pages/chat_page.dart | 测试: 36/36 绿 | 备注: 无
```

> 工人**不用**管合并、**不用**更新 04 文档、**不用**分配 M 编号——这些是收口时工头一次做的。

### 步骤 3 · 收口（工头会话执行，一次性把活并回来）

```powershell
# 先看各分支状态（谁没提交、谁测试没过）
powershell -File tools\parallel_dev.ps1 list

# 依次合并（--no-ff 保留分支历史，方便回滚）
powershell -File tools\parallel_dev.ps1 merge -Tasks "feat/voice-ui,feat/goal-card"
```

- **一路绿灯**：脚本自动合并完，接着做收口四步（见下）。
- **撞车了**（两个分支改了同一文件）：脚本会**停在那一个分支上**并把冲突文件列出来，不会硬并。
  处理办法：让工头会话（或你指定一个窗口）打开冲突文件，按 `<<<<<<<` 标记人工裁决，
  `git add` 之后执行 `powershell -File tools\parallel_dev.ps1 merge -Resume` 接着并剩下的。

**收口四步（合并后必做，粒度是"每批分支"而不是"每轮对话"）：**

1. `开发驱动文档/04-实现过程记录.md` 登记 M 编号（每个分支一条）
2. 必要时补 01/02/03 文档（有需求或方案变化时）
3. `E:\anaconda\python.exe verify.py` 必须全绿
4. `powershell -File tools\build_all.ps1` 重编 Windows 预览 + APK（**交付物铁律：合并后当轮重编**）

收完清理样板间：`powershell -File tools\parallel_dev.ps1 clean -Task "feat/voice-ui"`（删 worktree + 车间，代码已在 main 里，不丢）。

## 4. 冲突避雷（这是整套机制成败的关键）

**核心原则：按"文件"拆活，不按"功能点"拆活。**
两个任务如果都要动同一个文件，它们就不该并行——要么合并成一个任务，要么排队。

### 4.1 高危共享文件（能不碰就别碰，碰了就得排队）

| 文件 | 为什么高危 |
|---|---|
| `app/lib/main.dart` | 应用入口，谁加初始化逻辑都往这儿塞 |
| `app/lib/state.dart`、`app/lib/app_state_scope.dart` | 全局状态，加字段就是改这里 |
| `app/lib/data/*.dart` | 各库的读写层，多个功能常同时要加字段 |
| `app/pubspec.yaml` | 加依赖包必改；**一个周期只允许一个分支动它** |

### 4.2 派单时的三条自检（工头派单前必问）

1. **文件重叠吗？** 两个任务的文件清单有交集 → 不许并行。
2. **有依赖吗？** B 任务要用 A 任务新加的类/字段 → 不许并行，先 A 后 B。
3. **改 pubspec 吗？** 两个都要加包 → 合并成一个任务，或分开两批做。

### 4.3 真的撞了怎么办

- 小冲突（各改各的函数）：脚本列出冲突文件，工头会话直接裁决，`merge -Resume` 继续。
- 大冲突（同一段逻辑两种写法）：**停下来找老大定方案**，别让 AI 自己猜业务意图。

## 5. 已知坑（都是踩过的，照着躲）

| # | 坑 | 怎么躲 |
|---|---|---|
| 1 | **编译车间是独木桥**：两个会话同时用 `D:\sw_build`，源码互相覆盖、产物串味 | 每个分支必须用自己车间 `D:\sw_build-<短名>`；`build_all.ps1` 已支持 `-Project/-Workshop` 参数 |
| 2 | **pub get 并发抢锁**：多个车间同时拉依赖，pub 缓存锁会打架 | 派单时脚本已预热（串行跑）；工人会话中途要加包，先跟工头说一声错峰 |
| 3 | **worktree 里没有未跟踪文件**：预览 exe、本地 API 配置、`.workbuddy` 不会跟过去 | 分支里要测真实效果，重新配一次 API Key（或用导入的备份 JSON） |
| 4 | **磁盘**：每个车间约 1.6G，三个分支 ~5G | D 盘剩 180G 以上随便造；收口后记得 `clean` |
| 5 | **分支改文档 = 白改**：五文档只认 main，分支上的文档改动合并时会冲突且无效 | 分支只改代码+测试，文档留到收口 |
| 6 | ** Flutter 插件隐藏文件**：`.flutter-plugins*` 没同步到车间会导致插件注册失败 | `build_all.ps1` 已修复，同步时一并带上 |

## 6. 一次典型的"三开"剧本（照抄即可）

```
你（工头窗口，主目录）：
  ├─ 派单 A：new -Task feat/goal-card   -Goal "目标卡片支持折叠"     -Files app/lib/pages/goal_page.dart
  ├─ 派单 B：new -Task feat/notify-fix  -Goal "通知点击跳转修复"     -Files app/lib/pages/... 
  └─ 派单 C：new -Task feat/settings-ui -Goal "设置页分组重排"       -Files app/lib/pages/settings_page.dart
       ↓ 开 3 个对话窗口，分别切到 wt-goal-card / wt-notify-fix / wt-settings-ui，粘任务单
三个窗口同时开工（你去喝茶，不用守着）
       ↓ 陆续报 BRANCH_DONE
你（工头窗口）：merge -Tasks "feat/goal-card,feat/notify-fix,feat/settings-ui"
       ↓ 04 登记 3 条 M → verify 全绿 → build_all 重编 → 预览 exe 给老大验收
clean 三个分支
```

## 7. 什么时候**不该**并行

- 任务之间**文件或依赖有交集**（见 4.1/4.2）——并行省的时间全赔在解冲突上。
- 任务**本身要探索方案**（不知道要改哪些文件）——先单开一个 exp 分支摸清楚，再决定要不要拆。
- 只剩**一两个小改动**——开分支的开销（建目录+预热 1-3 分钟）比直接改还大。
- 需要**连续对话上下文**的深水区任务（比如调一个诡异 bug）——AI 需要来回看上下文，拆开反而慢。

## 8. 命令速查

```powershell
# 派单（建分支+目录+车间+任务单）
powershell -File tools\parallel_dev.ps1 new -Task "feat/xxx" -Goal "一句话目标" -Files "逗号分隔的文件" -Standard "完成标准"

# 查看所有并行任务状态
powershell -File tools\parallel_dev.ps1 list

# 批量合并收口
powershell -File tools\parallel_dev.ps1 merge -Tasks "feat/a,feat/b"
powershell -File tools\parallel_dev.ps1 merge -Resume        # 解完冲突继续

# 清理（合并后）
powershell -File tools\parallel_dev.ps1 clean -Task "feat/xxx"
powershell -File tools\parallel_dev.ps1 clean -All           # 清理所有已合并的分支
```
